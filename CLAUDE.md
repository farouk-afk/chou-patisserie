# Chou Pâtisserie — site vitrine

Marque fictive "Chou." — pâtisserie artisanale française (cookies, gâteaux, desserts). Site one-page en HTML/CSS/JS pur, sans framework ni build : tout vit dans `index.html`.

## Langage visuel

- **Palette** (custom properties CSS dans le `:root` de `index.html`) : `--cream`/`--cream-deep`/`--paper` (fonds ivoire), `--cacao`/`--cacao-soft` (texte chocolat), `--caramel`/`--caramel-deep`/`--praline` (accent ambré), `--pistache`/`--pistache-deep` (vert, réservé aux éléments pistache), `--rose`/`--rose-deep` (rose poudré, macarons/fruits rouges). `--rose-deep` a été ajouté pour `.field-error` : en thème clair c'est un rose-brique assombri (contraste ≥4.5:1 sur `--paper`/`--cream`), en thème sombre il vaut la même valeur que `--rose` (déjà accessible sur fond sombre). `--caramel-deep` (clair) a été légèrement assombri (`#8C4F20`) pour que `.p-badge--signature`/`.eyebrow` restent ≥4.5:1 sur fond `--cream-deep` (`#creations`, `#apropos`) ; la valeur du thème sombre n'a pas changé. Thème sombre complet via `@media (prefers-color-scheme: dark)` + `[data-theme]`.
- **Typographie** : Fraunces (serif display, titres) + Manrope (sans, corps/UI).
- **Illustrations** : les desserts sont de vraies photographies (Unsplash, licence libre), stockées localement dans `assets/img/*.webp` et référencées en chemin relatif (jamais d'hébergeur d'images externe — le CSP d'Artifact Claude bloque les images hors CDN autorisés). Hero (`.dessert-photo`) : chaque photo flottante est encadrée dans un médaillon circulaire (`border-radius:50%`, anneau `border:6px solid var(--paper)`, `object-fit:cover`) pour garder la lecture « dessert qui flotte » malgré le fond rectangulaire de la photo — toute nouvelle photo hero doit suivre ce même traitement en médaillon, pas un rectangle brut. Cartes créations (`.c-icon`) : photo pleine largeur en `object-fit:cover`, coins arrondis 20px, ratio 4/3 (16/9 pour les cartes `.big`). Galerie (`.g-item .art`) : photo en `object-fit:cover` plein cadre, `position:absolute; inset:0`. À propos (`.about-figure img`) : photo `object-fit:cover` remplissant le ratio 4/5 existant. Les anciens sprites SVG `<symbol>` (`#ic-*`, `#art-*`) ont été retirés du DOM, plus aucune trace à réutiliser.
- **Animation** : keyframes CSS pour les entrées et le flottement des desserts (transform/opacity uniquement), IntersectionObserver pour les révélations au scroll, parallax léger throttlé en rAF (desktop only, désactivé ≤920px et sous `prefers-reduced-motion`).
- **Mise en page** : grilles éditoriales asymétriques (cartes créations, galerie), pas de grille uniforme systématique.

## Structure de index.html

Navbar → Hero → Intro → Nos créations → Notre carte → Galerie → À propos → Marquee → CTA → Footer. Fichier unique, `<style>` et `<script>` inline, sprite SVG en haut du `<body>`.

**Notre carte** (`#carte`) : catalogue détaillé de 18 fiches produit (6 catégories × 1 classique/signature + 2 tendance), filtrable par pastilles (`.filter-pill`, JS vanilla, toggle de la classe `.p-hidden`, jamais d'affichage animé — pas de transition sur `display`). Chaque fiche (`.p-card`) suit le même langage visuel que `.c-card`/`.c-icon`/`.c-tag` : photo `object-fit:cover` en 4/3, coins arrondis, hover `translateY` + zoom léger de l'image, `h3` en Fraunces pour le nom (pas de `h4` : `#carte` n'a qu'un seul niveau de sous-titre sous son `h2`), description courte, ligne de prix (`.p-price`). Badge `.p-badge` en deux variantes réutilisant les tokens existants (jamais de nouvelle couleur en dur) : `--signature` (fond `--cream-deep`, texte `--caramel-deep`, même traitement que `.c-tag`) et `--tendance` (`color-mix` avec `--pistache`, pour signaler visuellement les nouveautés sans ajouter de token). Le reveal au scroll réutilise `.reveal` + l'IntersectionObserver existant, avec un stagger dédié à `.carte-grid` calqué sur celui de `.creations-grid`. Toute nouvelle fiche produit doit suivre ce même pattern (photo, badge signature/tendance, `data-category` pour le filtre, prix) plutôt qu'un composant parallèle. Les prix affichés sont des valeurs provisoires (voir commentaire HTML au-dessus de la section) à ajuster par le pâtissier. **Le temps de préparation** de chaque produit vit dans l'attribut `data-prep` du `.p-card` (ex. `data-prep="24h"`, `data-prep="4 à 5 jours (sur devis)"`) — toute nouvelle fiche doit définir cet attribut, c'est la seule source de vérité pour le calcul de date dans le formulaire de commande (voir plus bas). Ne pas dupliquer ces temps de prépa ailleurs dans le JS.

**Modale fiche produit + commande** : cliquer sur n'importe quelle `.p-card` (rôle `button`, `tabindex="0"`, clavier Entrée/Espace géré) ouvre `#productModal`, une seule modale réutilisée et repeuplée dynamiquement en JS (`extractProductData` lit `h4`, `.p-body p`, `.p-price`, l'image et le badge directement depuis la carte cliquée — ne jamais dupliquer ces textes en dur dans le JS). La modale a 3 états togglés via `hidden` sur leurs conteneurs (`showStep('product'|'form'|'confirm')`) :
1. **Fiche produit** — photo, badge, description (copy inchangée), prix, temps de préparation, stepper quantité (`#qtyInput`, min 1), bouton « Commander ».
2. **Formulaire de commande** — nom, téléphone, email (optionnel), mode de retrait (radio-pills « sur place » / « livraison », l'adresse de livraison n'apparaît que si « livraison » est choisi, via `.field-collapse` + classe `.open` — même trick `max-height` que `.c-card p` au hover, jamais de transition sur `height:auto`), date souhaitée (`<input type="date">` avec `min` et texte d'aide calculés dynamiquement depuis `data-prep` + la date du jour, voir `computeMinDate()`/`parsePrepHours()` — ne pas coder une date en dur), mode de paiement (radio-pills espèces / virement / **PayPal — préférence affichée uniquement, aucune intégration de paiement réelle n'existe sur ce site**, la note à ce sujet doit rester visible tant qu'aucune vraie intégration n'est branchée), message optionnel. Validation inline au submit (`.field-error`, 13px, couleur `--rose` — pas de nouveau token), focus posé sur le premier champ en erreur.
3. **Confirmation (EmailJS optionnel + repli mailto)** — le SDK EmailJS (`@emailjs/browser`, chargé depuis jsdelivr, seul CDN de script autorisé qui l'héberge) est inclus mais **inactif tant que `EMAILJS_SERVICE_ID`/`EMAILJS_TEMPLATE_ID`/`EMAILJS_PUBLIC_KEY` (dans le `<script>` principal, juste avant `currentProduct`) sont encore des placeholders `YOUR_...`** — dans ce cas le site se comporte exactement comme avant (lien mailto manuel uniquement, `#confirmManualState` affiché). Une fois ces 3 valeurs remplacées par de vraies clés EmailJS, chaque commande tente d'abord un envoi automatique via `emailjs.send(...)` ; en cas de succès `#confirmAutoState` s'affiche ("commande envoyée automatiquement"), en cas d'échec (réseau, quota EmailJS dépassé, etc.) le code retombe silencieusement sur `#confirmManualState` (même lien mailto qu'avant, rien ne casse). **EmailJS ne fonctionne pas dans l'aperçu Artifact** (requête réseau vers `api.emailjs.com` bloquée par son bac à sable) — uniquement sur un vrai déploiement du fichier. Le gabarit ("Email Template") côté EmailJS doit utiliser exactement ces variables : `product_name`, `quantity`, `unit_price`, `total`, `prep_time`, `customer_name`, `customer_phone`, `customer_email`, `pickup_mode`, `delivery_address`, `order_date`, `payment_method`, `message` — ne pas en renommer une sans mettre à jour `templateParams` dans le JS. — la commande n'est jamais « payée » ni « confirmée » ici : le JS construit un lien `mailto:farouk.b2012@icloud.com` (sujet + corps texte avec produit, quantité, prix unitaire, total calculé si le prix est numérique — sinon "sur devis" passe tel quel) et l'assigne à `#confirmMailtoLink`, un vrai `<a class="btn btn-primary">` bien visible ("Envoyer ma commande par email"). **Important : ce lien n'est jamais déclenché automatiquement via un clic JS synthétisé** (`.click()` sur un élément caché) — un clic script-only sur un lien `mailto:`/protocole externe est bloqué (page blanche) par le bac à sable de l'aperçu Artifact ; seul un vrai clic de l'utilisateur sur ce bouton fonctionne de façon fiable, aussi bien dans l'aperçu Artifact que sur un déploiement réel du fichier. Le texte affiché doit rester "commande prête à envoyer" + une instruction claire de cliquer pour l'envoyer, jamais "commande confirmée/payée" ni laisser croire qu'un email est parti automatiquement.

**Piège CSS à ne pas réintroduire** : chaque conteneur d'étape (`#modalProductView`, `#modalFormView`, `#modalConfirmView`) est montré/masqué via l'attribut `hidden` posé/retiré en JS (`showStep`). Si une classe appliquée à ce même élément définit `display` sans condition (ex. `display:flex`), cette règle d'auteur l'emporte sur le `display:none` natif de `[hidden]` (spécificité de classe > sélecteur d'attribut du UA) — l'étape reste visible en permanence, empilée avec les autres. C'est exactement ce qui s'est produit avec `.modal-confirm{ display:flex; ... }` : corrigé en retirant le `display` de la règle de base et en l'ajoutant uniquement via `.modal-confirm:not([hidden]){ display:flex; }`. Toute nouvelle étape de modale (ou tout nouvel élément togglé par `hidden`) doit suivre ce même pattern `:not([hidden])` si sa classe a besoin d'un `display` autre que le bloc par défaut.

Accessibilité de la modale : `role="dialog" aria-modal="true"`, focus déplacé dans le panneau à l'ouverture, piège de focus (Tab/Shift+Tab) tant qu'elle est ouverte, fermeture via Échap / clic sur le fond / bouton `.modal-close`, focus restauré sur la carte déclenchante à la fermeture. Animation d'ouverture/fermeture en opacity+transform uniquement (`.modal-backdrop`/`.modal-panel`), même trick `visibility` retardée que `.mobile-menu` pour l'attente de fin de transition avant `display:none`/`hidden`. Toute nouvelle modale du site doit réutiliser ce pattern plutôt qu'en inventer un nouveau.

**Fenêtre "Nous écrire" (`#contactModal`)** : le bouton `#openContactBtn` (dans le CTA final, classe `.btn-primary`, même couleur que "Commander maintenant") ouvre une modale simple — pas un lien `mailto:` direct, car les liens mailto ne fonctionnent pas de manière fiable sans application mail configurée sur l'appareil du visiteur. Deux vues togglées via `.hidden` (pas `showStep`, cette modale est plus simple que `#productModal`) : `#contactFormView` (email optionnel + `<textarea maxlength="1000">` avec compteur live `#contactCount`, validation inline si le message est vide) et `#contactConfirmView` (même sous-composant `.modal-confirm` + `#contactAutoState`/`#contactManualState` que la confirmation de commande). Réutilise **la même logique EmailJS/repli mailto** que le formulaire de commande (`emailjsReady`, `EMAILJS_SERVICE_ID`, `EMAILJS_TEMPLATE_ID`, `window.emailjs.send(...)`), en réemployant le même gabarit EmailJS que les commandes — les champs propres aux commandes (produit, quantité, prix...) sont remplis avec `'—'` et `product_name` vaut `'Message de contact (formulaire "Nous écrire")'` pour que Farouk distingue les deux types d'emails reçus sans avoir à créer un second template EmailJS. Le code de cette modale vit dans le même IIFE que `#productModal` (juste avant sa fermeture) pour réutiliser `getFocusable`, `reduced` et la config EmailJS déjà déclarés là — mêmes noms de variables préfixés `contact*` pour ne pas entrer en collision avec les `modal*`/`order*` existants.

**Cartes "Nos créations" → filtre de la carte** : chaque `.c-card` de `#creations` porte un lien `.c-more[data-goto="cookies|gateaux|desserts|tartes|brownies|custom"]` (style `.link-u`, cohérent avec les autres liens texte du site). Son clic appelle `applyCarteFilter(filter)` — la fonction unique aussi utilisée par les `.filter-pill` de `#carte`, jamais dupliquée — puis scrolle vers `#carte`. Toute nouvelle catégorie doit ajouter à la fois une pastille de filtre et le lien `.c-more` correspondant sur la carte créations concernée. `applyCarteFilter` est aussi exposée sur `window.applyCarteFilter` (une ligne, juste après sa définition) pour être réutilisée par l'assistant Chou décrit ci-dessous — ne jamais la redéfinir ou la dupliquer ailleurs.

**Assistant Chou (widget de chat, `.chat-widget`)** : bouton flottant fixe en bas à droite (`#chatLauncher`, cercle 58px, trois barres façon `.hamburger` qui se transforment en croix à l'ouverture) qui ouvre un panneau non-modal persistant (`#chatPanel`, `role="dialog"` **sans** `aria-modal` — le reste de la page reste interactif, contrairement à `#productModal`). C'est une FAQ scriptée, honnêtement présentée comme automatisée : ce n'est **ni une IA ni une personne réelle**, aucun appel réseau n'est fait. Cette mention reste visible en permanence dans l'en-tête du panneau (« Chou · assistant automatique » + sous-titre), pas seulement dans le message d'accueil qui peut défiler hors champ.
- **Données** : un tableau unique `CHAT_INTENTS` (dans le second `<script>`, tout en bas du fichier) où chaque entrée est `{ id, label, keywords:[...], reply, chips? }`. `label` sert à la fois de texte de pastille suggérée et de "message utilisateur" simulé affiché quand on clique la pastille. `chips` (optionnel, utilisé par l'intention "cadeau") propose des boutons `.chat-suggest-btn` qui appellent `window.applyCarteFilter(filter)` (le `filter` doit correspondre à une valeur `data-filter` existante de `#carte`) puis scrollent vers `#carte` et ferment le panneau — jamais de logique de filtrage réimplémentée ici. **Pour ajouter une nouvelle question/réponse : ajouter un objet à `CHAT_INTENTS`**, et si elle doit apparaître parmi les pastilles permanentes sous le fil de discussion, ajouter son `id` à `STARTER_ORDER`.
- **Correspondance** : `normalize()` retire les accents (minuscule + `String.prototype.normalize('NFD')` + suppression des diacritiques) avant un simple `indexOf` sur chaque mot-clé — aucune IA/NLP, juste du texte. Si rien ne correspond, réponse de repli honnête (`FALLBACK_HTML`), jamais une réponse inventée : elle propose un vrai lien `mailto:farouk.b2012@icloud.com` **et** un lien `https://wa.me/213555528051` (numéro WhatsApp de Farouk, format international sans "+" ni espaces, avec un message pré-rempli via `?text=`) — toujours garder les deux canaux à jour ensemble si l'un des deux change.
- **Accessibilité** : le journal de conversation `#chatLog` est `role="log" aria-live="polite"` (les réponses du bot sont annoncées sans voler le focus). Le focus est déplacé dans `#chatInput` à l'ouverture, Échap ferme et rend le focus à `#chatLauncher`, et — contrairement à `#productModal` — **aucun piège de focus** : Tab peut sortir du panneau vers le reste de la page, car il s'agit d'un widget non-modal.
- **Animation** : ouverture/fermeture en `opacity`+`transform` uniquement, avec le même trick `visibility` retardée que `.mobile-menu` (pas de `hidden` ajouté/retiré en JS pour ce panneau, tout passe par la classe `.open`) ; couvert par la règle globale `prefers-reduced-motion`.
- **Pastille d'invite** (`#chatPing`) : petit point qui pulse sur le bouton tant que l'assistant n'a jamais été ouvert sur ce navigateur (`localStorage.chouChatOpened`, avec repli silencieux si indisponible) — retirée dès la première ouverture.
- **Mobile (`≤640px`)** : le panneau devient une feuille quasi pleine largeur ancrée en bas (`left/right:16px`), toujours dans la marge minimale de 16px exigée par le projet ; le widget se masque tant que `.mobile-menu` plein écran est ouvert (écouteur dédié sur le clic du hamburger, sans toucher à son gestionnaire existant).
- Ce bloc JS est volontairement un second `<script>` séparé (IIFE distincte) après le script principal, pour ne jamais s'entremêler avec la modale/le filtre/le parallax — toute nouvelle intention ou tout nouveau comportement du chat doit rester dans ce bloc.

## Conventions

- Copy en français partout (marché francophone).
- Pas d'hébergeur d'images externe, pas de librairie JS lourde — vanilla sauf besoin réel avéré.
- `prefers-reduced-motion` et le chemin mobile simplifié doivent rester fonctionnels pour toute nouvelle animation.
- Couleurs toujours via les custom properties CSS, jamais de hex en dur dans une nouvelle règle.
- **Hiérarchie des titres** : un seul `h1` (titre hero), les titres de section sont des `h2`, et tout sous-titre à l'intérieur d'une section (fiches `.c-card`, fiches `.p-card` de `#carte`, colonnes du footer) est un `h3` — jamais de `h4`+ dans ce fichier tant qu'aucun niveau supplémentaire n'est réellement nécessaire, pour ne pas sauter de niveau. `.footer-col h3` a un `font-family:'Manrope'` explicite pour ne pas hériter du style serif des titres de section.
- **Accessibilité des champs de formulaire** : tout `.field-error` doit être relié à son champ via `aria-describedby` posé statiquement dans le HTML (pas seulement via `aria-invalid` en JS) ; les groupes de boutons radio (`.radio-pill`) relient chaque `input` à l'erreur du groupe de la même façon. Les éléments purement décoratifs/répétés visuellement (`.marquee-wrap`, `<span class="arrow">`) portent `aria-hidden="true"`. Le focus clavier des champs texte réutilise le même traitement `:focus-visible{ outline:2px solid var(--caramel); outline-offset:2px; }` que `.radio-pill`, jamais de `outline:none` sans remplacement visible.
- Les libellés de `.radio-pill` doivent tenir sur une seule ligne à ~360px de large (largeur réelle du panneau de la modale sur petit écran) : préférer un libellé court dans la pastille et garder le détail complet (adresse, précisions) dans le texte envoyé par email ou ailleurs sur la page plutôt que de tout répéter dans le libellé.
